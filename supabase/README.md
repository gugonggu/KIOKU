## 적용·검증

1. 호스팅 적용 전 앱의 Supabase URL과 CLI 대상의 프로젝트 참조를 대조합니다. 적용 이력과 기존 앱 테이블·데이터를 조회하고, 예정 파일이 일치하는지 DryRun으로 확인합니다. 프로젝트나 이력이 예상과 다르면 멈춥니다.
2. 기존 사용자 데이터에 영향을 주는 파괴적 변경이 필요하면 먼저 영향 범위를 확인하고 백업합니다. Free 플랜은 수동 논리 백업을 사용합니다. 스키마·데이터·권한과 마이그레이션 이력을 암호화된 위치에 보관하고, 필요한 Auth 설정과 Storage 파일 범위를 확인합니다. 운영 프로젝트에서 초기화나 이력 수정으로 문제를 해결하지 않습니다.
3. 기존 프로젝트에는 미적용 파일만 순서대로 적용합니다. M3는 PostgreSQL 15 이상이 필요하고 예전 장소 컬럼의 이름을 바꾸므로 앱과 스키마 전환을 맞춥니다. 적용 도중 오류가 발생하면 실제 커밋 상태와 이력을 조회하고 다음 작업을 결정합니다.
4. lint, typecheck, build, 관련 단위/DB 테스트를 실행하고, 실제 브라우저에서 변경된 핵심 흐름을 확인합니다. 로컬 PGlite와 모의 브라우저 API 테스트는 호스팅 Auth·PostgREST 확인과 별도로 기록합니다.

M4는 호스팅 적용 승인 후 M1~M3 이력을 확인하고 앱 전환 전에 적용합니다. 적용이 실패하면 트랜잭션과 적용 이력을 확인합니다. 이미 적용된 환경에서 문제가 생기면 예약 테이블과 일정 참조를 보존한 상태로 앱 배포를 멈추고 보정 마이그레이션으로 수정합니다. M3 전용 NULL 제약을 복원하려면 기존 예약과 연결의 보존 방안을 먼저 결정해야 합니다.

M5는 M4 적용과 확인에 이어 별도 승인 후 적용합니다. 적용 오류가 나면 트랜잭션과 이력을 확인합니다. 적용 후 공개 조회에 문제가 있으면 앱의 공유 경로와 `read_shared_trip` 실행 권한을 우선 차단하고, 기존 여행·예약·공유 상태를 보존한 상태로 보정합니다. 호스팅 검증에서 동행자 브라우저와 직접 Data API 호출을 함께 확인합니다.

호스팅 종단 간 점검은 가상 여행에서 **기존 계정으로 로그인 → 여행 생성 → 일정·장소 등록 → 항공·숙소·투어 등록 → 공유 발급 → 비로그인 창에서 HTML·JSON의 비공개 필드 차단 확인 → 공유 중지 후 같은 주소 재조회** 순서로 진행합니다. 링크 발급 전 서버 암호화 키와 실제 사용 주소의 HTTPS·로그 설정을 확인합니다.

2026-11-23 KIOKU 호스팅 PostgreSQL 17.12에 M2와 M3를 적용했습니다. 기존 M1 이력과 Auth 사용자 수를 유지했고, 세 앱 테이블의 RLS와 익명 SELECT 제한을 확인했습니다. 적용 전 여행은 0건이었으며 이 PC에서 덤프 도구를 실행할 수 없어 논리 백업은 생성하지 않았습니다.

기존 로그인 세션으로 Chrome에서 테스트 여행 생성, 일정·장소 추가·수정·삭제, 후보함 보관·복원, 일정과 장소 연결, OpenFreeMap 지도 핀, 로그아웃 후 보호 경로 차단을 확인했습니다. 장소 삭제 후 일정 행은 유지되고 장소 참조만 해제됐습니다. 두 번째 사용자 권한으로 DB 읽기 차단을 확인했습니다. 새 매직 링크 수신과 두 번째 계정의 실제 브라우저 로그인은 이번 검증에 포함되지 않았습니다. 로컬 검증은 lint, typecheck, build, 단위 9건, PGlite DB 12건, 모의 API Chrome E2E 26건을 통과했습니다.

2026-11-24 운영 카탈로그를 읽기 전용으로 다시 확인했습니다. M1~M5 버전이 모두 등록되어 있고, 공개 스키마의 여행·일정·장소·예약 테이블 8개에 RLS가 적용되어 있습니다. 이 8개 테이블과 비공개 공유 상태 테이블에 익명 테이블 읽기·쓰기 권한이 없습니다. 검토한 여행·일정·예약 RPC 12개 중 익명 실행은 `read_shared_trip`에만 허용됩니다. 운영 사용자와 여행 행을 변경하는 검증은 별도 승인 후 수행합니다.

## 호스팅 E2E 수용 기준

테스트용 여행과 장소로 핵심 흐름을 확인합니다. 두 계정에 접근할 수 있으면 별도 Chrome 프로필에서 소유자 격리도 확인합니다. 이메일 링크·세션·비공개 메모는 기록하지 않습니다.

| 단계 | 실행 및 기대 결과 |
| --- | --- |
| 실제 Auth·여행 CRUD | A와 B가 각각 매직 링크로 로그인합니다. A가 가상 여행 두 개를 만들고 목록·상세와 여행 수정을 확인합니다. 첫 여행에 3종 일정과 장소를 등록한 뒤 새로고침하고 재로그인해 ID와 데이터가 유지되는지 확인합니다. 참조 제한 확인 후 두 번째 테스트 여행을 삭제하고 목록에서 사라지는지 확인합니다. 로그아웃 후 보호 경로가 `/login`으로 이동해야 합니다. |
| 일정 이동·복원 | 날짜를 이동하고 후보함에 보관한 뒤 복원합니다. 같은 일정 ID, 시각·순서·메모·장소 참조가 유지되는지 확인합니다. 기간 밖 변경은 확인하기 전까지 저장되지 않아야 합니다. |
| 장소 연결·삭제 | 장소를 수정하고 두 일정에 반복 연결한 뒤, 일정 편집에서 한 연결을 해제하고 다시 연결합니다. 장소 삭제 확인에서 수량을 확인하고, 삭제 후 두 일정과 메모가 남으며 링크만 비워지는지 확인합니다. |
| M4 예약 연결·권한 | 가상 예약에서 미입력 항공 시각과 복수 구간, 숙소·투어 시각을 확인합니다. 일정 링크를 연결하고 삭제 전 미리보기와 일정 보존을 확인합니다. PostgREST에서 B와 익명의 예약 원본·비공개 상세 접근이 차단되어야 합니다. |
| M5 온라인 공유 | 가상 여행의 링크로 비로그인 HTML·JSON과 날짜 화면을 확인합니다. 범위 변경, 재발급, 만료, 중지 직후 다시 요청합니다. 익명 원본·쓰기·소유자 미리보기 차단과 프록시·접근 로그의 URL/요청 본문 비수집을 확인합니다. |
| 권한 격리 | A가 두 번째 여행의 장소를 첫 여행 일정에 연결하면 FK로 거부되어야 합니다. B의 A 여행·일정·장소 직접 URL 접근과 Data API 읽기·쓰기를 확인합니다. 익명 보호 페이지는 로그인으로 이동하고, 익명 Data API로 보호 데이터 조회·수정 함수 호출이 거부되어야 합니다. |
| 충돌·재시도 | 같은 계정 두 탭에서 같은 항목을 편집해 선행 저장만 유지되는지 확인합니다. 테스트 브라우저 한 탭에서만 일시적 네트워크 실패를 모의해 입력 유지·재시도와 중복 행 방지를 확인합니다. |
| 지도·폴백 | 데스크톱·모바일에서 핀, 날짜 필터, 명시적 위치 요청과 권한 거절, 외부 길찾기를 확인합니다. 검색 키 없음·API 오류·지도 로드 실패에도 수동 등록과 저장 목록이 유지되어야 합니다. |

## Geoapify 실검색 확인

현 어댑터는 주소와 장소명 제안을 지원하는 `/v1/geocode/autocomplete`에 `filter=countrycode:jp`와 요청 언어 `ko`·`ja`·`en`을 전달하고, 유효한 일본 좌표가 있는 결과를 최대 5개 표시합니다. POI 검색도 가능하지만 상점·식당과 다국어 별칭의 실제 검색 품질은 별도 확인합니다.

| 한국어 | 일본어 | 영어 |
| --- | --- | --- |
| 오도리 공원 | 大通公園 | Odori Park |
| 삿포로 TV 타워 | さっぽろテレビ塔 | Sapporo TV Tower |
| 오타루 운하 | 小樽運河 | Otaru Canal |
| 삿포로 맥주 박물관 | サッポロビール博物館 | Sapporo Beer Museum |

서버 환경의 `GEOAPIFY_API_KEY`에 승인된 키가 준비되면 위 12개 검색어를 순서대로 한 번씩 보냅니다. 결과 순위, 주소·지자체, 좌표의 유효성, 공식 관광 안내 위치와의 일치, 언어별 오탐을 기록합니다. 상점과 식당은 사전에 이름·주소가 확인된 후보로 각각 한 번씩 추가 검증할 수 있습니다. 총 14회 이내에서 시작하고 429가 나오면 멈춥니다. 검색 결과가 나온다는 사실만으로 정확성을 판정하지 않습니다. 이름으로 찾는 품질이 부족하면 Forward Geocoding을 비교하고, 알려진 권역에서 업종별 후보를 찾는 목적이라면 카테고리·지역 중심의 Places API를 비교합니다. 비교 호출은 별도 요청 한도를 합의한 후 실행합니다.
