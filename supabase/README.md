# M1~M3 여행 데이터베이스

[`20261122073111_create_trips.sql`](migrations/20261122073111_create_trips.sql)은 `public.trips`, 소유자별 RLS, 필드별 쓰기 권한, 수정 버전 트리거를 한 트랜잭션으로 추가합니다. 기존 Supabase Auth의 `auth.users`, `auth.uid()`, `auth.jwt()`를 사용합니다. 파일 버전은 KIOKU 테스트 DB의 적용 이력과 일치합니다.

[`20261123014445_create_trip_plan.sql`](migrations/20261123014445_create_trip_plan.sql)은 M2 `itinerary_items`, 같은 여행의 장소 참조용 `trip_places`, RLS와 일정 저장·배치·순서·기간 변경 함수를 추가합니다. 기존 여행 행이나 인증 설정은 변경하지 않습니다. `booking_id`는 M4에서 같은 여행의 예약 FK와 쓰기 권한을 도입하기 전까지 NULL만 허용합니다.

[`20261123022449_complete_trip_places.sql`](migrations/20261123022449_complete_trip_places.sql)은 M3의 다국어 장소명, 주소, 좌표·출처 검증 및 저장·삭제 함수를 추가합니다. M2의 이름과 주소는 컬럼 이름만 바꾸며 값과 장소 ID를 보존합니다. 같은 여행의 장소만 참조하는 복합 FK를 유지하고, 장소를 삭제하면 FK의 `place_id`만 NULL이 됩니다. 검색 호출 수는 공개 Data API에서 접근할 수 없는 `kioku_private` 스키마에 저장합니다. 검색어와 위치 이력은 이 테이블에 기록하지 않습니다.

## 적용

1. 로컬 Supabase CLI를 사용한다면 작업 폴더에서 최초 한 번 `supabase init`을 실행한 뒤 `supabase start`로 로컬 스택을 준비합니다. 실행 중인 로컬 스택에 적용하려면 `supabase migration up --local`을 사용합니다.
2. 승인된 호스팅 프로젝트에 반영하기 전 M1 적용 여부, M2 버전 미적용 여부, `trip_places`·`itinerary_items`·이전 `trip_schedule` 초안과의 충돌, 기존 데이터 백업을 확인합니다. 이전 초안이나 실제 일정 데이터가 존재하면 적용을 중단하고 별도의 데이터 보존 마이그레이션을 설계합니다. `public`이 Data API에 노출되는지와 테이블·함수의 명시적 권한을 확인한 뒤 순서대로 적용하고, M2 앱은 그 다음에 반영합니다.
3. 서로 다른 두 계정으로 각각 여행을 만든 뒤 자기 목록과 상세·편집·삭제 화면만 열리는지 확인합니다. 로그아웃 후에는 로그인 화면으로 이동합니다.
4. M3 전에 M2 이력과 M3 버전 미적용 여부, `kioku_private` 스키마 충돌 여부를 확인합니다. M3의 부분 `ON DELETE SET NULL` FK는 PostgreSQL 15 이상이 필요합니다. 기존 M2 앱은 예전 컬럼을 조회하므로 M3 스키마와 앱의 전환 시점을 맞추고, PostgREST의 스키마 갱신 여부를 확인합니다. 적용 후 기존 장소값·일정 참조, 삭제 후 연결 해제, 익명·다른 소유자 차단을 점검합니다.

## 검증과 복구

- `npm run test:db`가 매번 빈 로컬 PostgreSQL 엔진에 이 마이그레이션을 적용하고 소유자·비소유자·익명 역할을 검증합니다.
- 호스팅 적용 후 테스트 계정 두 개로 일정 생성·후보 복원·여행 기간 변경을 확인합니다. 익명 조회·함수 호출과 다른 여행의 일정·장소 참조가 거부되는지 확인합니다. PGlite와 브라우저 테스트용 API는 실제 호스팅 PostgREST 검증을 대체하지 않습니다.
- M3 적용 이후 앱 버전을 되돌릴 때는 새 다국어·출처 필드를 그대로 두고, 구버전의 이름·주소 조회를 복구할 호환 마이그레이션을 별도로 검토합니다. 삭제한 장소와 링크를 복원해야 하면 적용 전 백업에서 복구를 검증합니다.
- SQL 적용 중 오류가 나면 트랜잭션 전체가 롤백됩니다. 적용된 환경의 이력은 유지하고, 잘못된 정책이나 제약은 후속 마이그레이션으로 수정합니다.
- 여행이 저장된 이후에 마이그레이션 전 상태로 돌아가야 한다면 우선 데이터와 스키마를 백업하고 복구를 확인합니다. 여행 테이블을 제거하면 저장된 여행이 함께 사라지므로 별도 승인과 백업 확인 후에만 수행합니다.
- M1의 `cover_photo_id`는 빈 값만 허용합니다. 표지 사진 도입 단계에서 같은 여행의 사진을 가리키는 외래 키를 추가하면서 이 제약을 교체합니다.

## 실환경 적용 승인 전

1. 대상 프로젝트 참조를 로컬 설정과 대조하고, PostgreSQL 버전과 `supabase_migrations.schema_migrations` 이력을 읽기 전용으로 확인합니다. M1 `20261122073111`이 이미 적용돼 있으면 다시 적용하는 대신 컬럼·제약·트리거·RLS·권한을 대조합니다.
2. M2 `20261123014445`는 `itinerary_items`와 `trip_places`, 날짜·시간 제약, 같은 여행의 장소 FK, 소유자 RLS와 일정 함수를 추가합니다. M3 `20261123022449`는 기존 장소 이름·주소 컬럼의 이름을 바꾸고 다국어·출처 컬럼을 추가합니다. 장소 삭제 FK는 일정에서 `place_id`만 비우도록 바뀝니다. 검색 RPC는 인증된 해당 여행의 소유자만 호출할 수 있고, 호출 수는 비공개 스키마에 기록됩니다.
3. 원격 이력과 로컬 파일 목록을 비교한 뒤, 명시적으로 승인된 DB 접속 방식이 준비되면 CLI 3.2.0에서 `npx --yes supabase@3.2.0 db push --dry-run --skip-vault --remote`로 대상과 예정 목록을 다시 확인합니다. 위 명령은 이미 올바른 프로젝트에 링크된 체크아웃을 전제로 합니다. 이력이 어긋나거나 이미 존재하는 객체가 발견되면 중단하고, 원격 이력을 자동 수정하지 않습니다.
4. 적용 전 백업·복원 시점을 합의합니다. Free 프로젝트는 대시보드 백업이나 PITR에 의존하지 말고, 승인된 경로로 스키마·데이터·역할·마이그레이션 이력을 보관합니다. Auth 사용자와 Storage 객체까지 복구해야 하는 경우에는 DB 덤프 범위를 별도로 확인합니다. 백업은 Git 및 채팅 밖에 암호화해 보관하고, 격리된 환경에서 원본의 행 수·제약·접근 권한이 재현되는지 확인합니다.
5. 먼저 격리된 검증 프로젝트에서 적용합니다. 운영은 별도 승인 후 적용 직전 이력과 백업을 다시 확인합니다. M3의 컬럼 전환에 맞춰 앱 사용을 잠시 멈추고, M3 앱 전환 전까지 구버전 일정 화면을 사용하지 않습니다. 부분 실패 시 즉시 중단하고 각 마이그레이션의 실제 커밋 여부와 이력부터 재조회합니다. 이미 적용된 파일을 다시 돌리기 전에 호환 조치 또는 복구안을 검토합니다.

2026-11-23 사전 조사에서 호스팅 PostgreSQL 17.12에 M1만 적용되어 있고 로컬 M1 SQL과 일치함을 확인했습니다. `trips`는 0행이었고 익명 Data API 조회는 거부됐습니다. 관리 API가 반환한 물리 백업은 0건이며 PITR은 꺼져 있었습니다. CLI DryRun은 이 체크아웃에 프로젝트가 링크되지 않아 중단됐습니다. CLI가 프로젝트 참조로 연결할 때 임시 DB 로그인 역할을 만들 수 있으므로, 예정 목록은 읽기 전용 이력 비교로 확인했습니다. 적용 직전에 현재 상태를 다시 확인합니다. [CLI 3.2.0의 `db push` 부수 효과](https://github.com/supabase/cli/blob/v3.2.0/apps/cli/src/commands/db/push/SIDE_EFFECTS.md)

## 호스팅 E2E 수용 기준

검증은 승인된 격리 프로젝트와 테스트 계정 A·B만 사용합니다. 실제 사용자 데이터로 테스트하지 않습니다. 실행 기록에는 통과 여부, HTTP 상태, 변경 전후의 테스트용 행 수만 남기고 이메일 링크·세션·비공개 메모는 남기지 않습니다.

| 단계 | 실행 및 기대 결과 |
| --- | --- |
| A 생성·지속성 | A가 가상 여행 두 개를 만들고, 첫 여행에 3종 일정과 장소를 등록합니다. 새로고침하고 로그아웃·재로그인해 ID와 데이터가 유지되는지 확인합니다. |
| 일정 이동·복원 | 날짜를 이동하고 후보함에 보관한 뒤 복원합니다. 같은 일정 ID, 시각·순서·메모·장소 참조가 유지되는지 확인합니다. 기간 밖 변경은 확인하기 전까지 저장되지 않아야 합니다. |
| 장소 연결·삭제 | 장소를 수정하고 두 일정에 반복 연결한 뒤, 일정 편집에서 한 연결을 해제하고 다시 연결합니다. 장소 삭제 확인에서 수량을 확인하고, 삭제 후 두 일정과 메모가 남으며 링크만 비워지는지 확인합니다. |
| 권한 격리 | A가 두 번째 여행의 장소를 첫 여행 일정에 연결하면 FK로 거부되어야 합니다. B의 A 여행·일정·장소 직접 URL 접근과 Data API 읽기·쓰기를 확인합니다. 익명 보호 페이지는 로그인으로 이동하고, 익명 Data API로 보호 데이터 조회·수정 함수 호출이 거부되어야 합니다. |
| 충돌·재시도 | 같은 계정 두 탭에서 같은 항목을 편집해 선행 저장만 유지되는지 확인합니다. 테스트 브라우저 한 탭에서만 일시적 네트워크 실패를 모의해 입력 유지·재시도와 중복 행 방지를 확인합니다. |
| 지도·폴백 | 데스크톱·모바일에서 핀, 날짜 필터, 명시적 위치 요청과 권한 거절, 외부 길찾기를 확인합니다. 검색 키 없음·API 오류·지도 로드 실패에도 수동 등록과 저장 목록이 유지되어야 합니다. |

## Geoapify 실검색 확인

현 어댑터는 주소와 장소명 제안을 지원하는 `/v1/geocode/autocomplete`에 `filter=countrycode:jp`와 요청 언어 `ko`·`ja`·`en`을 전달하고, 유효한 일본 좌표가 있는 결과를 최대 5개 표시합니다. POI 검색도 가능하지만 상점·식당과 다국어 별칭의 실제 검색 품질은 별도 확인합니다.

| 한국어 | 일본어 | 영어 |
| --- | --- | --- |
| 오도리 공원 | 大通公園 | Odori Park |
| 삿포로 TV 타워 | さっぽろテレビ塔 | Sapporo TV Tower |
| 오타루 운하 | 小樽運河 | Otaru Canal |
| 삿포로 맥주 박물관 | サッポロビール博物館 | Sapporo Beer Museum |

서버 환경의 `GEOAPIFY_API_KEY`에 승인된 키가 준비되면 위 12개 검색어를 순서대로 한 번씩 보냅니다. 결과 순위, 주소·지자체, 좌표의 유효성, 공식 관광 안내 위치와의 일치, 언어별 오탐을 기록합니다. 상점과 식당은 사전에 이름·주소가 확인된 후보로 각각 한 번씩 추가 검증할 수 있습니다. 총 14회 이내에서 시작하고 429가 나오면 멈춥니다. 검색 결과가 나온다는 사실만으로 정확성을 판정하지 않습니다. 테스트 결과로 현재 엔드포인트의 적합성을 평가한 뒤, 보완 필요 시 Geocoding 또는 Places API를 비교합니다.
